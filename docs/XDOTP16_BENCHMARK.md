# XDOTP16 效益量測（FIR / 內積 / 矩陣乘）

目的：用實際 kernel 比較「使用自訂指令 `XDOTP16`」與「只用標準指令」的週期數，量化加速比。
同一顆 CPU（IP 1.6）、同一份 bitstream，只換程式。

> 狀態：RTL 模擬週期數已確認（12 支程式的 DMEM 結果與黃金模型逐字一致，重複執行的週期為常數）；
> 實板（IP 1.6）執行 `RV32I_CPU_Benchmark.ipynb`：**24 / 24 PASS**，板上週期數與模擬一致（誤差 < 0.1%），見 3b 節。

## 1. Kernel 與實作

| Kernel | 內容（資料皆為有號 int16，結果 int32） | MAC 數 |
|---|---|---|
| `dot` | 128 元素內積（每次迴圈 8 個元素，迭代 16 次） | 128 |
| `fir` | 8 taps、16 個輸出：`y[n] = Σ h[k]·x[n+k]` | 128 |
| `matmul` | 8x8 矩陣乘 `C = A x B`（B 以轉置存放） | 512 |

| 代號 | 實作 | 資料格式 |
|---|---|---|
| S0 | 純標量，`lw` + `mul` + `add` | 未打包：每個 int16 佔一個字 |
| S1 | 標量，用 `slli` / `srai` 拆包（RV32I + MUL） | 打包：兩個 int16 一個字 |
| S2 | 同 S1，但用 Zbb `sext_h` 拆包 | 打包 |
| X | `xdotp16`：一條指令 = 2 個乘加 | 打包 |

S0 是「不需要拆包」的標量下限，也是最公平的對照組；S1 / S2 代表資料已打包、但只有標準指令時的做法。

## 2. 公平性設計

- 四種實作都經過同一個 list scheduler（只重排、不改指令；避開 load-use stall），所以 stall 週期全為 0。
- 每次迴圈處理的元素數相同（dot 8 個、FIR 2 個輸出、matmul 每個內圈 2 個輸出）。
- 打包資料的 FIR 需要「偶數對齊」與「奇數對齊」兩份 x（核心沒有 `lh`，無法對半字取值），額外記憶體算在 S1 / S2 / X 身上。
- 輸入資料由 PS 事先寫入 DMEM，載入時間不算；kernel 內的 setup（指標、常數）算在內。
- 週期數 = reset 放開後到「spin 指令第一次進入 EX」的 cycle 數（含 pipeline 填充）。
  用 `ex_pc` / `ex_valid` 判斷，而不是 IF 的 PC，因為 IF 會在分支解析前預取到 spin 位址（wrong-path）。

## 3. 結果（RTL 模擬，單次執行）

加速比 = 基準週期 ÷ 該實作週期。`CPI` = 週期 ÷ 指令數。

|---|---|---|---|---|---|---|---|---|
| dot | S0 | 41 | 565 | 1.06 | 598 | 1.00x | 1.43x | 1.21x |
| dot | S1 | 57 | 821 | 1.04 | 854 | 0.70x | 1.00x | 0.85x |
| dot | S2 | 49 | 693 | 1.05 | 726 | 0.82x | 1.18x | 1.00x |
| dot | **X** | **25** | **309** | 1.11 | **342** | **1.75x** | **2.50x** | **2.12x** |
| fir | S0 | 56 | 363 | 1.05 | 380 | 1.00x | 1.53x | 1.35x |
| fir | S1 | 89 | 564 | 1.03 | 581 | 0.65x | 1.00x | 0.88x |
| fir | S2 | 77 | 496 | 1.03 | 513 | 0.74x | 1.13x | 1.00x |
| fir | **X** | **37** | **232** | 1.07 | **249** | **1.53x** | **2.33x** | **2.06x** |
| matmul | S0 | 67 | 1724 | 1.04 | 1789 | 1.00x | 1.32x | 1.16x |
| matmul | S1 | 91 | 2300 | 1.03 | 2365 | 0.76x | 1.00x | 0.88x |
| matmul | S2 | 79 | 2012 | 1.03 | 2077 | 0.86x | 1.14x | 1.00x |

| Kernel | S0 | X |
|---|---|---|
| dot | 0.214 | 0.374 |
| fir | 0.337 | 0.514 |
| matmul | 0.286 | 0.518 |

### 重點

1. **XDOTP16 比最強的純標量（S0）快 1.5 到 1.8 倍；比「資料已打包、只能用標準指令」的做法（S1 / S2）快 2.1 到 2.5 倍。**
2. 資料打包本身（S1、S2）在沒有 XDOTP16 時反而更慢（0.65x 到 0.86x），因為拆包要多出 shift / `sext_h` 指令；打包只有搭配 XDOTP16 才有好處。
3. 靜態程式也更小：dot 25 字 vs 41 字（S0）。
4. 加速比低於理論上的 2 倍（乘加數減半），原因是迴圈的 load、指標更新與分支開銷不會變少，加上 FIR 要處理兩份對齊資料。
5. stall 全為 0（排程避開了 load-use）；週期比指令數多的部分來自 pipeline 填充與 taken branch 的 flush
   （每次 taken 浪費 2 個 bubble；dot 16 次 flush、fir 8 次、matmul 32 次）。
6. 與 Vivado 數據合併看：XDOTP16 多用 2 個 DSP48E2，WNS 仍為正（+1.977 ns）；換來上述加速。

## 3b. 實板結果（PYNQ-ZU，IP 1.6，2026-10-18）

`RV32I_CPU_Benchmark.ipynb` 實板執行：**24 / 24 PASS**（12 項結果正確 + 12 項計時）。
報告檔：`pynq_5-stage-pipeline-CPU_TEST/cpu_bench_report_ip1.6_24of24.json`。

- **正確性**：12 支程式執行後，整塊 DMEM（1024 字）與黃金模型預期逐字一致。
- **計時**：每支程式重複 R 次（總時間約 0.267 秒），板上每次重複的週期數 = 時間 x 時脈 ÷ R，
  與 RTL 模擬值的比值介於 **1.0005 到 1.0007**（誤差約 0.05% 到 0.07%，遠小於 2% 的門檻）。
  差距來自 PS 以 MMIO 輪詢結束時多出的幾十到幾百微秒。

### 注意：這次實測的 PL 時脈是 187.5 MHz，不是 100 MHz

- PYNQ 回報 `Clocks.fclk0_mhz` = **187.498 MHz**；上表的比值是用這個時脈換算的，
  與模擬值吻合到 0.07%，代表板子實際就跑在約 187.5 MHz（若實際是 100 MHz，比值會是 1.87，會判定失敗）。
- Vivado 的時序報告（WNS +1.979 ns）是以 **100 MHz（10 ns）約束**簽核的，關鍵路徑約 8 ns，依 slack 的估算上限約 125 MHz。
  187.5 MHz（週期 5.33 ns）**超出 Vivado 的簽核範圍**：它代表這顆晶片在這個溫度下、這些測試上實際可運作，
  不是時序保證，也不能當作 fmax 規格。

**原因（2026-10-18 在板上讀 CRL_APB 暫存器診斷）**

| | Block Design（`.hwh`） | 板上實際 |
|---|---|---|
| PL0 時脈來源（`SRCSEL`） | RPLL | **IOPLL**（`SRCSEL` = 0） |
| 分頻 `DIVISOR0` / `DIVISOR1` | 8 / 1 | 8 / 1 |
| PLL 輸出 | RPLL：33.333 x 48 ÷ 2（`DIV2`）= 800 MHz | IOPLL 約 1500 MHz（由 fclk0 反推，未直接讀 IOPLL 暫存器） |
| PL0 頻率 | 800 ÷ 8 = **100 MHz** | 1500 ÷ 8 = **187.5 MHz** |

- PS 的 PLL 與 PL0 的時脈來源是由 PYNQ 的開機映像決定的，bitstream 與 Block Design 並不會把它們改成 BD 裡設定的值；
  PYNQ 載入 overlay 時只套用 `.hwh` 的分頻（÷8÷1），所以 Vivado 以為的 100 MHz 與板上的 187.5 MHz 不同。
- 板上 RPLL 暫存器讀到 `FBDIV` = 45、`DIV2` = 1（750 MHz），但 PL0 並沒有使用 RPLL，這個讀值與時脈無關。
- 註：暫存器的值會跨 Kernel 保留，所以「載入前 fclk0 已是 187.498」並不能區分是 PYNQ 載入 overlay 時設的，還是映像預設值；兩者結論相同。
- **影響**：先前的實板測試（Notebook v3 的 40/40、v4、v5 的 52/52，以及本次 24/24）很可能都是在 187.5 MHz 下完成
  （這是依本次診斷的推定，當時沒有逐次記錄時脈）。這些測試驗證的是功能與週期數，不是時序簽核；
  週期數與加速比與時脈無關，所以本文的結論不受影響，但「板上 100 MHz」的說法不準確。
- **處理**：Notebook v5 與 `RV32I_CPU_Benchmark.ipynb` 的 cell ① 已加入 `Clocks.fclk0_mhz = 100`（`TARGET_CLK_MHZ`，可設為 `None` 不改），
  並在改時脈前讓 CPU 留在 reset、讀回實際頻率後才換算週期數。下一步是在 100 MHz 下重跑兩本 Notebook，得到落在簽核範圍內的板測結果。
  若要把 187.5 MHz 當作設計目標，需在 Vivado 把 `pl_clk0` 改成 187.5 MHz 重新 Implementation，檢查 WNS（以目前約 8 ns 的關鍵路徑，預期不會滿足）。

## 4. 重複執行：週期為常數

每支程式另有「重複 R 次」的版本（`x31` 為計數器）。R = 2 與 R = 3 的週期差（即每次重複的週期）
= 單次週期 + 1（重複迴圈的 `addi` + `bne`，扣掉不重複的填充），皆為常數，因此板上可用 R 很大的版本量時間。

## 5. 板上版（`pynq_5-stage-pipeline-CPU_TEST/RV32I_CPU_Benchmark.ipynb`）

PS 端用 `time.perf_counter()` 量時間，不需要硬體計數器：

1. cell ④ 正確性：PS 寫入資料與程式 → run → 讀回整塊 DMEM（1024 字）與預期結果逐字比對（12 項）。
2. cell ⑤ 計時：把 `li x31, R` 換成使總時間約 0.5 秒的 R，換算 `cycles/rep = 時間 x 時脈 ÷ R`，
   與 RTL 模擬的 rep 週期比較，容許誤差 2%（12 項）。
3. cell ⑥ 總表與 `cpu_bench_report.json`。

需要 IP 1.6 的 bitstream（`FEATURE` = 0x17）。Notebook 自包含（程式、資料、預期結果、模擬週期都嵌在 cell ②），板上不需要 Python 黃金模型。
共 24 項檢查；預期全過。上板前以模擬的 MMIO（由 Python 黃金模型代為執行）把 cell ① 到 ⑥ 完整跑過，24 / 24 通過，驗證的是 Notebook 邏輯，不是硬體。

### 為什麼板上比值可能略偏離 1.0

PS 以 MMIO 輪詢 PC，延遲為微秒等級，相對 0.5 秒可忽略；`Clocks.fclk0_mhz` 讀不到時假設 100 MHz，
Notebook 已在 cell ① 把時脈設為 100 MHz 並讀回實際值（`TARGET_CLK_MHZ`）；換算用的是讀回的頻率（原先未設定時讀到 187.498 MHz，見 3b 節）。

## 6. 重現方式

```bash
python3 tools/gen_bench.py          # 產生 sim/bench/*（程式、資料、預期結果、manifest）
cd sim && python3 run_bench.py      # iverilog 逐支模擬，輸出週期數與 bench_results.json（需要 iverilog）
python3 ../tools/gen_bench_notebook.py   # 產生板上 Notebook
```

`tb_bench.v` 是 testbench；`gen_bench.py` 內建黃金模型檢查（每支程式在模型上執行到 spin，並檢查預期結果）。

## 7. 限制

- 週期數以 RTL 模擬為準，板上計時已驗證一致；但第一次實測時 PL 時脈為 187.5 MHz（PYNQ 預設，與 BD 的 100 MHz 不同），超出 Vivado 簽核範圍（見 3b 節）；Notebook 已改為先設 100 MHz，待重跑。
- 只比較三個 kernel；矩陣 / FIR 規模小（受 4 KB DMEM 限制）。
- 結果是整數內積；沒有量化、飽和或浮點。
- 加速比反映本核心的特性（單發射、乘法為單週期 DSP、無 `lh`）；在其他核心上不能直接套用。
